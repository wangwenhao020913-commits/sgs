# 一将一票：票面骨架（Batch Ticket）

新增一个武将 = **一张票** = 一次门禁 = 一次提交。本文件是那张票的骨架与 DoD，复制成
`.scratch/<effort>/issues/<NN>-<slug>.md` 用（`.scratch/` 不进版本库）。

票面字段遵守 `docs/agents/issue-tracker.md`：`Status:` 一行、可选 `Touches:` / `Ruling:` /
`规则原文:`；开工先置 `Status: claimed`，收口写 `## Answer` 再置 `Status: resolved`。

## DoD（两条腿）

| 腿 | 判据 |
|---|---|
| **已实现** | 有能红的回归（先写红再修绿）；相关单文件绿；`smoke-web` 绿；金录像不变 |
| **已摘出** | 有裁定票（`Status: open`）、票面写明命中哪条硬停、本票的「摘出记录」指过去 |

**不许**出现第三种状态（"做了一半"）。批次收口时若还有技能悬着，本票不置 `resolved`。

## 门禁与提交节奏

| 时点 | 动作 |
|---|---|
| 迭代期（逐技能） | `.venv/bin/pytest -q tests/test_hero_<包>.py`；`bash tests/smoke-web.sh`；`bash tools/check_goldens.sh`。**不提交** |
| 批次收口 | `bash tests/run_all.sh --quiet`（一次） |
| 提交 | 一次 commit（不做 `wip:` 提交——hook 对 `wip:` 也跑全量） |
| 实机验收 | 只有新增询问形态 / 改 DOM 形状才做；配方写进票面（`## 复现配方`） |

## 为什么是"一将一票"

- 一个武将的几条技能通常共享同一个包、同一个测试文件、同一批金录像判断 —— 拆成 N 张票，
  N 次门禁全是重复劳动。
- 但**硬停仍然按技能粒度**：某条技能命中硬停时只摘出它，其余照做。批次的 DoD 用"已实现 /
  已摘出"两条腿收口，所以摘出不会让整批陪葬，也不会被掩盖。
- 若同一武将的两条技能**互相依赖**（后一条要用前一条的落点），在批次清单里写明顺序，
  但仍是一张票、一次门禁。
