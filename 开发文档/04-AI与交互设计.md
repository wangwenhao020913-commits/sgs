# 04 AI 与交互设计

本文件定义“谁来做决策、怎么把决策送进引擎、怎么把过程展示出来”。

---

## 1. 参与者接口（统一抽象）

人类、AI、脚本玩家对引擎而言是**同一种东西**：一个能对 Query 作答的
参与者。统一接口的输入输出：

| 方向 | 内容 |
|---|---|
| 入（引擎 → 参与者） | Query（类型、候选行动、可见信息、时限） |
| 出（参与者 → 引擎） | Action（选择结果 / 放弃 / 超时） |

好处：
- 测试时把人类替换成脚本玩家，即可自动跑完整局；
- AI 与人类共用同一条协议，前端只是“人类的适配器”。

> **响应窗口是“收集式”，不是一问一答（依据票 19 §9 / 票 28）**：无懈可击窗口这类响应
> 窗口，引擎在窗口期内向**多个应答者**依次发出询问、把所有应答**收集**起来，**再一次性
> 推进**（按询问顺序取优先级最高者真正生效）；不是“问一个、等它把整个结算走完再问下一
> 个”的同步问答。记录流形态固定为每层 **N 次询问 + N 次应答**（N = 本层存活数），赢家
> 之后才继续原锦囊结算。`respond(query)` 的**契约不变**——入仍是 Query、出仍是 Action，
> 收集与推进都由引擎侧负责（见 `02` §5「询问 / 响应模型」）。

## 2. 信息可见性

| 信息 | 可见范围 |
|---|---|
| 自己的手牌 | 仅自己 |
| 他人手牌数量 | 公开 |
| 装备区 / 判定区 / 武将牌上的牌 | 公开 |
| 武将牌 / 势力 | 公开（标准版明置） |
| 身份 | 主公公开；其余死亡时公开 |
| 牌堆顺序 | 仅引擎（技能“观看牌堆顶”按效果逐张授予） |
| 已公开 / 展示过的牌 | 对相关方公开 |

**硬性要求**：引擎生成 Query 前必须按可见性过滤；全知信息不得下发，
否则 AI 会作弊、回放会泄露。

## 3. AI 分层设计

按投入产出比分三层，逐层增强：

### 3.1 第一层：合法随机（基线）
- 从“合法行动集合”中随机选择。
- 作用：验证引擎、提供最弱对手、作为性能基准。

### 3.2 第二层：规则启发式（MVP 推荐）
- 核心是**启发式评分**：对每个候选行动打分，取最高分（可加少量随机）。
- 需要处理的决策点：出牌、响应（是否出闪/杀/无懈）、目标选择、
  技能发动、弃牌选择、濒死是否用桃。
- 评分要素示例：
  - 我方收益：伤害期望、手牌增益、关键牌保留；
  - 敌方损失：优先压低血线、优先集火反贼/主公；
  - 身份推断：根据行为估计他人身份（对忠臣/反贼/内奸不同策略）；
  - 资源：手牌上限、距离与攻击范围、装备价值；
  - 风险：是否会被集火、是否暴露身份。

> **M3 落地（依据票 13；ADR-011）**：第二层的落点是 `src/sgs/agents/heuristic.py` 的
> `HeuristicPlayer`——只满足既有的 `Participant` 协议（入 Query、出 Action），不引入第二套接口。
> 结构 = 按 `QueryKind` 分派 → 每类一个打分函数（`score = 我方收益 − 敌方损失 − 自伤风险`）
> → 取最高分；平分由 `"ai"` 子流打破（同种子逐字节可复现）。
> **档位**：`cli --ai random|heuristic`，**缺省仍是随机**——默认参与者不动，M2 的回放基准磁带一行不改。
>
> **特征清单**（只取可从 `query.view` 与 action **局部算出**的量）：伤害期望、牌数增减、
> 体力增减、距离 / 攻击范围、手牌上限、目标数。**权重是数值，不进本文件。**
>
> | 询问 | 默认策略 |
> |---|---|
> | `PLAY_PHASE` | 能造成伤害且目标非己方 ＞ 装备 ＞ 过牌；手里留【桃】/【闪】，除非能一次斩杀 |
> | `DODGE` / `RESPOND` | 能抵消就抵消（响应牌不占使用次数） |
> | `PEACH` | 救（桃用于救命几乎恒正收益），除非自己是濒死链的下一个 |
> | `DISCARD` | 弃价值最低（【桃】/【闪】最后弃，装备按槽位价值排序） |
> | `SKILL_ACTIVATION` | 查**技能语义表**，缺省 `Pass`（**拿不准就不发动**） |
> | `SELECT_CARDS` / `SELECT_OPTION` | 按上面的特征贪心 |
> | `ARRANGE` | 最有用的牌留顶（按牌名价值表） |
>
> **技能语义表**：键 = 技能 id，住 AI 模块；**正向断言**"启用的每名武将的每个非锁定技能都有条目"、
> **反向断言**"表里每个 id 都在数据里存在"，两条都 fail-closed ⇒ "加了武将但忘了教 AI"立刻判红。
>
> **改判（ADR-011）**：上面那条"**身份推断**：根据行为估计他人身份"以及风险项里的
> "是否暴露身份"**不做**——AI 面对"不知道谁是敌人"时的默认策略是**保守 + 局面量**，
> 不是猜身份；这条由"只读可见面"的硬约束保证。

### 3.3 第三层：搜索 / 学习（后续）
- 对关键决策做有限的向前搜索（考虑隐藏信息时需采样）。
- 训练型 AI 所需的状态编码、动作编码沿用引擎的 Event 与 Action 结构。

### 3.4 AI 工程约束
- AI **只能**通过可见信息与合法行动集合决策，禁止访问全知状态；
  M3 把这条钉到两个具体读点：`query.view` 与 `query.legal_actions`。
- **AI 决策时限 + 超时默认动作不进 M3（改判 M4，见 ADR-011）**：超时机制与"单一随机源 /
  禁时间依赖"两条既有纪律冲突，属**接入层**（会话 / 网络）的事；M3 的启发式 AI 是同步纯函数，
  只做一次评分、不设时限、也不会返回"超时"。
- AI 通过 `agents` 目录独立演进，不污染 `rules-core`。

## 4. 人类交互设计

### 4.1 交互原则
- 前端只做两件事：**渲染事件流**、**收集并提交 Action**。
- 合法性由引擎判定；前端可高亮合法目标，但不能自行裁决。
- 隐藏信息在传输层即被过滤，前端不接收未公开数据。

### 4.2 界面形态演进
| 阶段 | 形态 | 目的 |
|---|---|---|
| M1 | 命令行 | 最快验证规则 |
| M2 | 极简 Web（文字 + 头像 + 手牌按钮） | 可用性 |
| M3 | **无界面**（沿用命令行） | 专注规则与 AI |
| M4 | 图形化牌桌、动画 | 体验 |

> **改判（以 `06` §2「MVP 范围裁剪表」为准）**：本节原写"M3 = 图形化牌桌、动画"**已改判**——
> 里程碑文档把**动画 / 音效**判为 ❌、把**人类 UI** 判为 ⏳ M4，故 **M3 无界面**（沿用命令行），
> 图形化牌桌与动画一并归 M4。

## 5. 交互协议（接入层）

| 消息 | 方向 | 说明 |
|---|---|---|
| 加入 / 准备 | 客户端 → 服务端 | 建立会话 |
| 状态快照 | 服务端 → 客户端 | 连接或重连时下发可见状态 |
| 事件流 | 服务端 → 客户端 | 增量事件，驱动界面 |
| 询问 | 服务端 → 客户端 | Query + 候选行动 + 时限 |
| 应答 | 客户端 → 服务端 | Action |
| 结束 | 服务端 → 客户端 | 胜负方与统计 |

协议要求：
- 事件带序号，支持断线重连后增量补齐；
- 询问带超时，超时按预设策略代为决策；
- 同一局的事件流对观战者可做延迟 / 隐藏处理。

---

## 6. 观战与回放

- 回放 = 种子 + Action 序列；引擎重放产生同一事件流。
- 回放支持任意时刻快照，用于复盘与教学。
- 观战模式复用事件流，但按“上帝视角开关”决定是否显示隐藏信息。

---

## 7. 可观测性与调试

- 每个事件携带“时机 + 触发者 + 原因”，便于定位“为什么这里触发了技能”。
- 提供两种视角：玩家视角（过滤后）与全知视角（调试用）。
- 规则争议时，直接导出该回合的全知事件日志作为证据。
