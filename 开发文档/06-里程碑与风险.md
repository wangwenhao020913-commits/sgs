# 06 里程碑与风险

---

## 1. 里程碑规划

### M0 规则与设计冻结（当前阶段）
- 交付：规则文档缺口补齐；本套开发文档；文档校验测试通过。
- 验收：`tests/run_all.sh` 全绿；规则存疑点全部登记为决策项。
- 产出物：`三国杀详细规则.txt` + `开发文档/`。

### M1 引擎骨架可跑通最小对局
- 范围：状态模型、时机枚举、结算栈、行动校验、脚本玩家。
- 内容：仅【杀】【闪】【桃】+ 无武将；无身份 1v1（2 人）；命令行。
- 验收：可完整打完一局；同种子结果一致；单元测试覆盖使用全步骤。
- 风险最高点：**结算栈与插入结算**是否正确。

### M2 标准版身份局
- 范围：108 张牌、判定、延时锦囊、无懈可击、濒死、死亡奖惩、
  身份胜负、4～8 人配置。
- 验收：Golden Replay 用例 ≥ 30 条；不变量 fuzz 无失败。
- 关键验证：无懈嵌套、目标时机、同时死亡判定。

### M3 标准版武将 + 启发式 AI
- 范围：**16 名**标准版武将（覆盖 A–I 九族机制 + J–N 顺带族）；随机 AI + 启发式 AI。
  **无界面**（沿用命令行；见 §2「MVP 范围裁剪表」的"人类 UI ⏳ M4 / 动画 ❌"）。
- 验收（**三条机械判据**，逐条定义见 `.scratch/m3-standard-heroes/spec.md` §Acceptance）：
  1. **每个机制族都有构造局面实测**——A–I 每族 ≥1 条（落点 `tests/test_hero_skills.py`）；
  2. **一局 5 人全 AI 可无人干预跑完并给出正确胜负**——固定 5 人、**32 个种子**，
     判据 = 跑完 ∧ 终局记录与身份胜负一致 ∧ 零非法应答 ∧ 可回放；
  3. **门禁全绿**——`bash tests/run_all.sh`（5 个 shell 校验 + 全部 pytest）。
- 关键验证：**逐点触发**（受 1 点伤害逐点触发；伤害减为 0 则一次都不触发）、**改判循环**、
  **求助窗口**、**失去牌后**、**目标池排除**。
- 与本节原文的两处已裁定偏离（第 0 票回写）：① "12～15 名" → **16 名**
  （数量是机制覆盖的结果、不是判据）；② 验收从一句话拆成上面三条机械判据。

### M4 可用界面 + 完整标准局
- 范围：极简 Web 界面、事件流渲染、询问应答、超时兜底、回放；
  接入层落点 = **`tools/sgs_web/`**（`src/sgs/` 一行不改；形态见 ADR-012）。
- 验收（**三条机械判据**，逐条定义见 `.scratch/m4-web-ui/spec.md` §Acceptance）：
  1. **端到端人类局**——经真 HTTP 跑完一局 **8 人**身份局，人类座位逐个回答自己的每一次询问，
     判据 = 跑完 ∧ 终局与身份胜负一致 ∧ **零非法应答** ∧ 每次询问都真的经过 HTTP 往返
     （落点 `tests/test_web.sh`；`tests/test_web.py`）；
  2. **不泄露**——给人类座位下发的任何字节里，对手座位只有**手牌数量**与公开区、
     身份只出现"本人 / 主公 / 已阵亡"三种可见情形、牌堆只有数量无顺序（落点 `tests/test_web.py`）；
  3. **回放闭环**——该局**记录流**经引擎重放逐行相同，且逐座位武将能从**侧车元数据**放回原位
     （落点 `tests/test_web.py`）。
- 关键验证：**等待人类不进引擎**（**挂起驱动**：人类座位只让引擎退到**暂停点**，
  应答由接入层送回）、**可见性只在投影处过滤**、**超时代答是纯函数且不进记录流**。
- 与本节原文的已裁定细化（见 ADR-012 变更块）：
  ① "极简 Web" 的形态从 ADR-005 的 WebSocket + React **改判**为标准库 HTTP + 手写 HTML/JS；
  ② 验收从一句话拆成上面三条机械判据；③ **托管（AI 代打）保留为功能、不进判据**。

### M5 军争篇
- 范围：52 张牌、属性伤害、连环传导、【酒】、藤甲 / 白银狮子。
- 验收：属性与连环专项测试通过；AI 会使用 / 防范属性伤害。
- 注意：军争显著提高伤害上限，需要重跑平衡性相关的 AI 测试。

### 后续（非 MVP）
界限突破（宝物槽位 + 界武将）→ 国战（暗置 / 明置 / 野心家）→
联机匹配 → 搜索型 AI。

## 2. MVP 范围裁剪表

| 功能 | MVP | 理由 |
|---|---|---|
| 身份局 | ✅ | 核心玩法 |
| 标准版 108 张 | ✅ | 规则基础 |
| 军争篇 | ⏳ M5 | 增加伤害与连环复杂度 |

| 联机 | ❌ | 单机跑通再谈 |
| 动画 / 音效 | ❌ | 不影响正确性 |

## 3. 风险清单与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 结算时机实现错误 | 规则不可信，全盘返工 | 先建时机枚举与栈；用官方 FAQ 建 Replay |
| 技能硬编码进流程 | 加武将越来越难 | 数据驱动 + 效果原语；禁止技能逻辑进主干；机械判据 = 源码纪律扫描（`tests/test_source_discipline.py` §5） |
| 隐藏信息泄露 | AI 作弊、回放失真 | Query 生成前强制可见性过滤 |
| 规则版本混淆 | 行为不一致 | 内容包 + 规则版本配置，显式声明 |
| 存疑点未决 | 实现反复 | 全部登记为决策项，在 `06` §4「决策记录（ADR）」与 §5「程序化约定与偏离一手」逐条裁定并落文档 |
| 非确定性 bug | 无法复现 | 单一随机源 + 事件日志 + 禁止时间/顺序依赖 |
| 范围蔓延 | 迟迟跑不通一局 | 严守 MVP 裁剪表，M1 先只做杀闪桃 |
| 数据录入错误 | 隐蔽的规则错误 | 加载期结构 + 语义校验；牌堆分布断言 |

> 新增本案，同时**改判 ADR-005 的两项**。`01` §4「技术选型」冻结的接入层选型是
> "FastAPI + WebSocket + React"，M4 取 **标准库 HTTP（轮询）+ 手写 HTML/JS**：

> 所以接入层无论怎么放，**等待人类都不能是线程或协程**——它只能是"请求还没来"。
>
> **等待人类的落地形态 = 挂起驱动**：人类座位的参与者只让引擎退到**暂停点**，
> 应答由接入层送回（`Engine.pending` 与 `Engine.submit` 本来就是公开面，故**引擎一行不改**）。
> 这条路径在 M4 设计期被实测：一局里 43 次挂起 / 续跑，**询问序号零重复**、**记录流与
> "不挂起的一次性跑法"逐字节相同**、**再经磁带重放仍逐字节相同**。

> **冲突说明（ADR-005 改判的代价与理由）**：这不是"技术栈降级"，而是**把不可验证的依赖
> 换成可验证的标准库**——`.venv` 里只有 pydantic + pytest，PyPI 抓取极慢，而 M4 的立身之本是
> "不需要网络与界面即可验证"（`01` §7「非功能需求」）。WebSocket 与 React 的**收益**（推送、组件化）
> 在单机单人类场景下都换不到东西；代价（依赖安装、构建步骤、多一条与规则无关的失败面）
> 却要由门禁承担。**改回去 = 重新裁定**，须先解决依赖与构建链的可复现性。

> 而 ADR-011 同时冻结了"AI 是同步纯函数、不设时限"。两者并存的唯一收法是：
> **只有人类有超时**，代答是**纯函数**（优先 `Pass` → 其次 `EndPhase` → 再退 `legal_actions[0]`；
> 只读询问、不取随机、不读时钟），且**不进记录流**——超时是接入层的事实，
> **记录流**仍是引擎的真源，故回放逐字节可复现不受影响。

> **ADR-012 变更说明（第二次；依据牌桌交互重构的设计闭环，`.scratch/m4-manual-select/spec.md` 的 D1–D18）**：
> **候选改为「内联集合 + 按牌索引」两份一起下发**。M4 首版把**合法行动集合**原样铺成按钮
> （每条候选一个），而候选是引擎枚举的**牌 × 目标组合**直积（实测：单张牌的候选最多 **80** 条、
> 一次询问最大 **87** 条），玩家面对的是"从几十条预先组合好的句子里挑一条"，而不是"点牌 → 点目标"。
>
> **改判的是"下发的形状"，不是"合法性的来源"**：`legal_actions` 仍然保留（超时兜底、提交前的
> 逐字段自我核对、既有测试都读它），新增的 `candidate_index` 是它**按牌聚合的索引**
> （`{card_id: {card, pool, min_targets, max_targets, combos}}`）。两者"同源"由一条断言机械钉死：
> 池与组合 ⊆ 候选、候选 ⊆ 索引、索引不含任何规则判定（距离 / 攻击范围 / 花色 / 体力 / 存活）、
> 前端不构造 `Action` 对象只做查找。故本变更**没有**在本层重新实现规则。
>
> **界面同批改为"手选卡牌 + 手选目标"**：**焦点** ≠ **已选定**（界面高亮可点范围时不读焦点）；
> 目标的合法性只问"这组座位在不在候选里"；**自动选中**只在"合法组合恰好一组、且那组就是池的全部"
> 时触发（【南蛮入侵】这类"目标即全部角色"的牌），并明确**不自动提交**。
> 松判据 `池大小 == 最少目标数` 是**错的**：借刀杀人的被迫【杀】是"池 4、目标数 1、组合 4 条"，
> 它会把 4 个座位全自动选中，而玩家真正要做的是四选一。
>

> **ADR-013 变更说明（依据 W6-Q6 / Q9 与实现；`.scratch/w6-skill-pipeline/spec.md` §4.2 / §4.3）**：
> 新增本案 —— 把"排列"从**某条技能的手写回调**提成**可复用类型 + 通用界面契约**。

> **为什么不是每条技能各写一套**：排列在规则上只做三件事（看牌堆顶 X 张 → 排顺序与切分 →

> - **只两档切分**：`free`（全部切分点，观星）与 `fixed`（只一个切分点）。`fixed` 的
>   `top + bottom` 必须**恰好等于**本次张数——对不上是**声明错误**（定数在构造期抛、
>   可调用档在 `split_point` 抛），不是运行期状态。
> - **`Arrange` 不进预发动清单、也不能由复合动作预填**：排列的候选是"全部排列 × 切分点"，
>   不是可选池（`Step.pool` 表达不了）。将来的 `preactivated` 排列技能要另立票。
> - **不落 `destination` 字段**：本期只有牌堆顶 / 牌堆底两个去处，没有读取方的配置不落。
> - **帧私有 peek 缓存的已知边界**：缓存键 = `(流水线名, 步骤序号)`，**不含"第几次发动"**
>   —— 同一帧里同一条流水线发动第二次会命中第一次看的牌。当前**没有消费者**会这样，故
>   W6 只登记、不改键形状（改键要同时看 `Engine.ask_arrange` 的答案键）。
