# 01 总体设计

## 1. 项目目标与范围

### 1.1 目标
用最小成本做出一个**规则正确、可复现、可扩展**的《三国杀》单机/联机
MVP：能完整跑通一局身份局，人类可操作、AI 可托管、结果可回放。

### 1.2 MVP 范围（做什么）
- 模式（里程碑口径，回写依据票 13 §3 / 票 04）：最终形态 = 身份局 **4～8 人**；
  **M1 = 无身份 1v1（2 人，已完成）**；M2 = 标准版身份局 4～8 人。
- 牌堆：标准版 108 张（军争篇作为第二阶段接入）。
- 武将：先 12～15 名，覆盖不同时机类型作为引擎验证样本。
- 玩家：1 名人类 + 若干 AI，或全 AI 观战。
- 交互：命令行 / 极简 Web 界面二选一先做其一。

### 1.3 明确不做（非目标）
- 军争篇、界限突破、国战、暗置/明置（首期不做）。
- 精美动画、音效、皮肤、账号系统、匹配与排行榜。
- 移动端原生客户端。

### 1.4 成功标准
1. 同一随机种子 + 同一行动序列，两次运行产生完全一致的事件日志与终局。
2. 规则文档第 3、4、6、8、11～17 章涉及的机制均有对应测试通过。
3. 一局 5 人 AI 对局可无人干预跑完并给出正确胜负方。

## 2. 设计原则

1. **正确性优先于性能与画面**：三国杀的难点全在结算时机，先把规则跑对。
2. **确定性**：所有随机来自单一种子发生器；不依赖系统时间、并发顺序。
3. **逻辑与表现分离**：引擎不感知 UI；UI 只是事件的渲染器。
4. **数据与逻辑分离**：牌、武将、技能以数据描述，引擎只提供效果原语。
5. **纯状态推进**：核心推进函数不产生副作用，输入“状态 + 行动”，
   输出“新状态 + 事件列表”。
6. **一切可观测**：每次状态变化都产出结构化事件，供回放、调试、AI 使用。
7. **规则可配置**：版本差异通过配置开关切换，而非改代码；存疑点在 `06` §4「决策记录（ADR）」与 §5
   「程序化约定与偏离一手」逐条裁定并落文档。

## 3. 总体架构

分层（上层依赖下层，反向不依赖）：

```
┌───────────────────────────────────────────────┐
│ 表现层 UI       命令行 / Web 前端 / 观战回放    │
├───────────────────────────────────────────────┤
│ 接入层 Server   会话管理、请求应答、超时、重连  │
├───────────────────────────────────────────────┤
│ 参与者层 Agents 人类适配器 / AI / 脚本玩家      │
├───────────────────────────────────────────────┤
│ 规则引擎 rules-core                            │
│   ├─ 状态 State                                │
│   ├─ 时机 Timing                               │
│   ├─ 事件与结算栈 Resolution Stack             │
│   ├─ 询问/响应 Query-Response                  │
│   └─ 行动校验 Action Validation                │
├───────────────────────────────────────────────┤
│ 数据层 data     卡牌表 / 武将表 / 技能定义      │
└───────────────────────────────────────────────┘
```

**关键约束**：`rules-core` 不允许 import UI、网络、AI 的任何模块；
`Agents` 只能通过统一的“参与者接口”与引擎交互。

## 4. 技术选型

### 4.1 推荐方案
| 层 | 选型 | 理由 |
|---|---|---|
| 引擎 | Python 3.11+ | 迭代快、测试生态成熟、类型注解 + 数据校验完善 |
| 数据校验 | pydantic 类模型 | 卡牌/武将数据在加载期即校验，避免脏数据进引擎 |
| 测试 | pytest | 规则回归、参数化用例、fixture 组织清晰 |
| 服务 | FastAPI + WebSocket | 与引擎同语言，推送事件流天然适配 |
| 前端 | TypeScript + React | 生态成熟；只消费事件流，不承载规则 |
| 存储 | 本地 JSON / SQLite | MVP 阶段无需数据库集群 |

### 4.2 备选方案
- **TypeScript 全栈**：引擎可在浏览器运行，联机成本低；适合以 Web
  为主要形态、希望前后端同构的团队。缺点是规则测试生态略弱。
- **不推荐首期使用**：C++/Rust（开发慢）、Unity/Pygame（画面不是瓶颈，
  会拖慢规则验证）。

### 4.3 选型结论
**推荐 Python 引擎 + WebSocket + React 前端**。若团队更熟悉前端，
可整体换成 TypeScript，架构设计不变。

## 5. 模块划分

| 模块 | 职责 | 依赖 |
|---|---|---|
| `data` | 加载/校验卡牌、武将、技能定义 | 只读依赖环 `data → effects → state → data`（加载期跨层校验只读） |
| `state` | 定义对局状态、区域、角色、牌实例 | data |
| `timing` | 时机枚举与时点调度 | state |
| `resolution` | 结算栈、插入结算、恢复主流程 | timing |
| `effects` | 效果原语库（造成伤害、摸牌、弃牌等） | state |
| `skills` | 技能定义与注册（挂到时机上） | effects |
| `engine` | 对外门面：初始化、推进、查询合法行动 | 以上全部 |
| `agents` | 人类适配器、AI、脚本玩家 | engine（只读接口） |
| `server` | 会话、协议、推送 | engine, agents |
| `ui` | 渲染事件流与收集输入 | server |

## 6. 关键数据流：一次行动的生命周期

```
玩家/AI 产生 Action
      ↓
引擎校验 Action 合法性（不合规则拒绝并返回原因）
      ↓
应用 Action → 改变状态
      ↓
按当前时机依次触发技能与效果
      ↓
若需玩家决策 → 生成 Query，暂停并等待应答（可能多次往返）
      ↓
若产生插入事件（伤害/濒死/连环/无懈）→ 压栈，先结算内层
      ↓
内层结算完毕 → 出栈，继续被中断的流程
      ↓
持续产出事件（Event）→ 追加到事件日志
      ↓
直到对局结束或等待下一次输入
```

要点：**“生成 Query → 等待应答”是唯一的暂停点**，其余流程尽量一气
呵成，保证可回放与可测试。

## 7. 非功能需求

| 维度 | 要求 |
|---|---|
| 确定性 | 同种子同输入 → 同输出；无隐式全局随机 |
| 可复现 | 事件日志可完整重放一局 |
| 可测试 | 核心逻辑无需网络与界面即可运行 |
| 可扩展 | 新增武將 = 新增数据 + 效果组合，不改引擎主干 |
| 性能 | 单步结算在毫秒级；AI 决策可配置时限 |
| 可观测 | 每次状态变更都有事件与原因（谁触发、哪个时机） |
| 容错 | 非法输入被拒绝而非导致状态损坏 |

## 8. 版本与扩展策略

1. **规则版本作为配置**：`standard` / `standard+ex`（军争）/ `boundary`
   （界限突破）通过配置选择，引擎主干不变。
2. **内容包**：卡牌与武将按“包”组织，可单独启停（如**宝物槽位**随界限突破、
   **军争属性伤害 / 连环**随军争篇引入——这些都是**合法**的规则开关，与存疑点无关）。
3. **存疑点裁定**：不建配置开关；逐条裁定并记录于
   [06 文档](06-里程碑与风险.md) 的 §4 与 §5「程序化约定与偏离一手」。
4. **向后兼容**：数据模型与事件结构带版本号，便于旧回放兼容。
